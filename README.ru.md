# Beauty Multimaster Bot

[English](./README.md) | **Русский**

Telegram-бот онлайн-записи для бьюти-мастеров. Один сервис обслуживает сразу много независимых мастеров: у каждого свой бот со своим названием, аватаркой и токеном, а работают они все на одном приложении, одной базе PostgreSQL и одном планировщике.

Клиент выбирает услугу, дату и время и записывается без переписки. Мастер ведёт расписание, услуги, клиентов и статистику из админ-панели в своём боте. Для владельца сервиса есть отдельный закрытый бот, через который он управляет мастерами.

Интерфейс бота на русском. Тексты, которые мастер может менять (подтверждения, напоминания, приветствие), хранятся отдельно для каждого мастера.

## Возможности

### Клиенту

- Запись в несколько нажатий: услуга, дата в календаре (дни без свободного времени помечены), время, подтверждение. Свободные слоты считаются с учётом рабочих часов, обеда, закрытого времени, особых дней, длительности услуги и перерыва после неё.
- В разделе «Услуги и цены» под каждой услугой есть кнопка «Записаться». Она ведёт сразу к выбору даты для этой услуги, а список услуг из чата убирается.
- «Мои записи»: будущие записи, перенос и отмена (перенос мастер может отключить).
- Портфолио с фотографиями и отзывы (от 1 до 5 звёзд, их можно редактировать).
- «Проверить время»: картинка выбранного дня со свободным и занятым временем.
- Напоминания за 24 часа и за 2 часа до визита. Подтвердить, перенести или отменить запись можно прямо из сообщения.
- Лимит активных записей. Когда он исчерпан, клиент отправляет мастеру запрос, мастер принимает или отклоняет его (можно с комментарием). Принятый запрос даёт одну дополнительную запись.
- Ссылки-приглашения: мастер создаёт запись для человека, которого ещё нет в боте, и отправляет ему ссылку `t.me/<бот>?start=inv_<токен>`. По ссылке запись привязывается к этому человеку.

### Мастеру (админ-панель в его боте)

- Расписание: рабочие часы по дням недели, обед, исключения на конкретные даты (открыть одну субботу, закрыть один день). Если на такую дату уже есть подтверждённые записи, бот предупреждает.
- Записи: списки на неделю и на месяц, ручное создание записи (в том числе для клиента без Telegram), отмена с уведомлением клиента, закрытие и открытие времени.
- Услуги и цены: создание, переименование, смена цены, длительность и перерыв после услуги, включение, отключение и удаление. Прошлые записи сохраняют исходные данные.
- Статистика за сегодня, неделю, месяц, три и шесть месяцев: число записей, фактическая и ожидаемая выручка, свободные часы. Плюс Excel-отчёт за выбранный период.
- Контент: приветствие, «Обо мне», «Как меня найти», портфолио, модерация отзывов.
- Клиенты и доступ: после серии отмен подряд мастер получает предупреждение и может ограничить клиента. Ограниченный клиент может отправить одно сообщение, а мастер решает, вернуть ему доступ или ограничить насовсем.
- Настройки: шаг записи (15, 30 или 60 минут), какие напоминания включены, лимит активных записей, порог отмен, перенос и отзывы, валюта, свои тексты сообщений с подстановками.
- Тихий режим: ежедневное окно, в которое бот не беспокоит мастера. Уведомления копятся и приходят по порядку, когда окно закончится.
- Личные напоминания для самого мастера (разовые, ежедневные, еженедельные, ежемесячные, ежегодные). Считаются по местному времени мастера, поэтому не уезжают при переходе на летнее время.
- «Мой бот»: статус, проверка подключения, повторная регистрация webhook. Токен нигде не показывается.

### Владельцу сервиса (суперадмин-бот)

Отдельный бот отвечает только Telegram-id из белого списка, остальным не отвечает вообще.

- Создание мастеров, подключение и отключение их ботов, смена владельца, включение и отключение мастера. Данные при этом не удаляются.
- Сводка: сколько мастеров, ботов, клиентов и записей, без персональных данных.
- Пробный период: срок служит только напоминанием о том, что пора принять решение, сам по себе ничего не отключается. Раз в день приходит сводка по мастерам, у которых срок подходит или уже вышел.
- Мониторинг: оповещения, если Telegram отклонил токен бота, webhook пропал или указывает не туда, появились ошибки доставки.
- Журнал действий: кто, что, с каким мастером и когда сделал, и чем закончилось. Токены и секреты туда не попадают.
- Эталонный мастер: мастера 1 можно сохранить как шаблон и одним действием вернуть к нему любого демо-мастера (профиль, услуги, расписание, портфолио, тексты, аватарка бота).

## Как это устроено

```
Telegram
   |  POST /tg/{bot_id}/{secret}      свой URL у каждого бота
   v
Caddy (автоматический HTTPS)  ->  FastAPI + aiogram 3 (один процесс приложения)
                                       |
                  +--------------------+---------------------+
                  |                    |                     |
              handlers  ->   services  ->  repositories  ->  PostgreSQL
              (Telegram)     (бизнес-      (SQLAlchemy 2,     (все данные,
                              логика)       всегда в рамках    напоминания,
                                            одного мастера)    ограничения)
                  |
                  +-> Redis (только состояние диалогов)
                  +-> APScheduler (напоминания всех мастеров, один планировщик)
```

Бизнес-логика лежит в `app/services`, а не в обработчиках. Обработчик принимает апдейт и вызывает сервис, сервис ходит в базу через репозитории.

**Мультиарендность.** Мастер определяется по тому боту, в который пришёл апдейт. В каждой таблице с данными мастера есть `master_id`, каждый репозиторий создаётся под конкретного мастера, и запросы фильтруются по нему. Это держится не на договорённости, а на тестах-сторожах (см. [Тесты](#тесты)).

**Два режима запуска** (`RUN_MODE`):

| Режим | Что делает | Когда нужен |
| --- | --- | --- |
| `polling` (по умолчанию) | Один бот из `BOT_TOKEN`, один мастер из `MASTER_ID`, long polling | Разработка, один мастер |
| `webhook` | Много ботов: у каждого мастера своя запись в таблице `master_bots`, апдейты приходят по HTTPS | Продакшен, много мастеров на одном сервисе |

## Решения, о которых стоит знать

- Двойную запись на одно время запрещает сама PostgreSQL: GiST-ограничение исключения по `(master_id, time_range)` для подтверждённых записей. Даже при гонке два пересекающихся бронирования не создадутся. Есть тест, который шлёт два параллельных запроса на один слот в настоящую базу.
- Напоминания переживают перезапуск. Это строки в таблице `notifications`, а не таймеры в памяти. Строки забираются через `FOR UPDATE SKIP LOCKED`, поэтому параллельные воркеры не отправят дубль.
- Запись хранит снимок услуги (название, цену, длительность) на момент бронирования. Смена прайса не переписывает историю.
- Токены ботов хранятся зашифрованными (Fernet, `BOT_TOKEN_ENCRYPTION_KEY`) и не попадают в логи и вывод. Сообщение с токеном удаляется сразу после получения. В URL webhook есть секрет бота, а заголовок `X-Telegram-Bot-Api-Secret-Token` проверяется сравнением за постоянное время.
- Состояние диалогов лежит в Redis, поэтому незаконченные диалоги (запись, отзыв, ввод услуги) переживают деплой. Ключи содержат id бота и сами истекают.
- Один планировщик на всех мастеров. Сбои изолированы: плохой токен или флуд-лимит у одного бота не останавливает напоминания остальных. Отправка ограничена по скорости на каждого бота. Advisory-блокировка PostgreSQL не даёт двум пересекающимся процессам (например, при плавном обновлении) выполнить один и тот же тик.
- Защита webhook от перегрузки. Число одновременных апдейтов ограничено до того, как берётся соединение с базой, поэтому один медленный бот не вычерпает пул. Когда очередь полна, сервис отвечает 503, и Telegram повторяет запрос позже.
- База хранит время в UTC. Часовой пояс мастера (по умолчанию `Europe/Minsk`) нужен для отображения и повторов. Менять его из бота пока нельзя, только в базе.

Подробности и причины решений описаны в [ARCHITECTURE.md](./ARCHITECTURE.md) (на русском).

## Стек

- Python 3.12
- aiogram 3.15
- FastAPI и uvicorn (режим webhook)
- PostgreSQL 16, SQLAlchemy 2 (async, asyncpg), Alembic
- Redis 7 для состояния диалогов
- APScheduler
- Caddy 2 с автоматическим HTTPS
- pydantic-settings, cryptography (Fernet), Pillow (картинка расписания), openpyxl (Excel-отчёты)
- Docker и Docker Compose
- pytest и pytest-asyncio, тесты идут на настоящих PostgreSQL и Redis

## Локальный запуск

Понадобятся Docker с Compose и токен бота от [@BotFather](https://t.me/BotFather).

1. Создайте файл окружения и заполните его:

   ```bash
   cp .env.example .env
   ```

   Минимум:

   ```env
   BOT_TOKEN=            # от @BotFather (/newbot)
   ADMIN_TELEGRAM_ID=    # ваш числовой Telegram id, например из @userinfobot
   MASTER_ID=1
   TIMEZONE=Europe/Minsk
   ```

2. Запустите стек (PostgreSQL, Redis, бот). Миграции применяются сами при старте.

   ```bash
   docker compose up --build
   ```

3. Откройте бота в Telegram, отправьте `/start`, затем `/admin`, чтобы попасть в админ-панель.

4. По желанию заполните базу демо-данными:

   ```bash
   docker compose exec bot python -m app.seed
   ```

`ADMIN_TELEGRAM_ID` задаёт только начального владельца. При старте он записывается в `masters.owner_telegram_id`, если у мастера ещё нет владельца. Дальше источником правды остаётся владелец из базы.

### Без Docker

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements-dev.txt

# PostgreSQL должен работать, база создана, расширение включено:
psql -c "CREATE EXTENSION IF NOT EXISTS btree_gist;" beauty_bot

cp .env.example .env     # DATABASE_URL направьте на localhost
alembic upgrade head
python -m app.main
```

## Конфигурация

Все настройки берутся из переменных окружения. Полный список с комментариями лежит в [.env.example](./.env.example). Основное:

| Переменная | Назначение |
| --- | --- |
| `RUN_MODE` | `polling` (по умолчанию) или `webhook` |
| `BOT_TOKEN` | Токен бота, только для режима polling |
| `ADMIN_TELEGRAM_ID` | Начальный владелец мастера `MASTER_ID` |
| `MASTER_ID` | Какого мастера обслуживает polling-бот |
| `DATABASE_URL` | `postgresql+asyncpg://...` |
| `REDIS_URL`, `FSM_STORAGE` | Хранилище диалогов. По умолчанию `memory` для polling и `redis` для webhook |
| `PUBLIC_BASE_URL` | Публичный https-адрес, обязателен для webhook |
| `BOT_TOKEN_ENCRYPTION_KEY` | Ключ Fernet для хранимых токенов, обязателен для webhook |
| `SUPERADMIN_BOT_TOKEN`, `SUPERADMIN_TELEGRAM_IDS` | Включают суперадмин-бота и задают, кому он отвечает |
| `TRIAL_DEFAULT_DAYS`, `SUPERADMIN_DIGEST_HOUR`, `SUPERADMIN_TIMEZONE` | Пробный период и ежедневная сводка |
| `DB_POOL_SIZE`, `DB_MAX_OVERFLOW`, `WEBHOOK_MAX_CONCURRENT_UPDATES` | Пул соединений и лимиты webhook |
| `SCHEDULER_*` | Параллельность, скорость отправки и таймауты планировщика |

Настройки мастера (шаг записи, напоминания, лимиты, валюта, тексты, тихий режим) в переменные окружения не выносятся. Мастер меняет их в боте, в разделе «Настройки».

Ключ шифрования генерируется так:

```bash
python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
```

## Продакшен

`docker-compose.prod.yml` поднимает весь стек: приложение в режиме webhook, PostgreSQL 16, Redis и Caddy с автоматическим HTTPS. Наружу открыты только порты 80 и 443, PostgreSQL и Redis видны лишь внутри сети compose.

```bash
cp .env.example .env     # заполните блок PRODUCTION
docker compose -f docker-compose.prod.yml up -d --build
```

Что нужно до первого запуска:

1. Сервер с Docker и домен, у которого A-запись указывает на этот сервер. Порты 80 и 443 должны быть открыты.
2. В `.env`: `PUBLIC_DOMAIN` (без `https://`), `POSTGRES_PASSWORD` (только буквы и цифры), `BOT_TOKEN_ENCRYPTION_KEY`, `SUPERADMIN_BOT_TOKEN`, `SUPERADMIN_TELEGRAM_IDS`. Если обязательное значение не задано, compose не запустится.
3. В `deploy/Caddyfile`: свой email для уведомлений Let's Encrypt.

На что обратить внимание:

- Запускайте ровно один экземпляр приложения. Планировщик рассчитан на один процесс. Не используйте `--scale app=2` и не поднимайте второй стек на той же базе, иначе напоминания задвоятся.
- Храните копию `.env` и ключа шифрования вне сервера. Без ключа сохранённые токены ботов не расшифровать, и каждого бота придётся подключать заново.
- Проверки состояния: `GET /health` (процесс жив) и `GET /ready` (отвечают база и Redis). Через Caddy `/ready` наружу не отдаётся.
- Бэкапы: `tools/backup/backup.sh` делает проверенный сжатый дамп с ротацией на 14 дней, `tools/backup/restore.sh` проверяет, что дамп действительно разворачивается. Настройка по расписанию описана в `tools/backup/SCHEDULE.md`.
- Обновление и откат, репетиция миграций на свежем дампе и чек-лист перед запуском описаны в [docs/OPERATIONS.md](./docs/OPERATIONS.md) (на русском).

Новый мастер добавляется в суперадмин-боте в два шага: создать мастера с Telegram-id владельца, затем подключить токен бота, который мастер получил у @BotFather. Сервис проверит токен, сохранит его зашифрованным и зарегистрирует webhook.

## Управление мастерами

Основной интерфейс это суперадмин-бот. Те же операции доступны из командной строки:

```bash
docker compose -f docker-compose.prod.yml exec app python -m app.cli create-master --owner-telegram-id 123456789 [--trial-days 14]
BOT_TOKEN_TO_ADD='<токен>' docker compose -f docker-compose.prod.yml exec -e BOT_TOKEN_TO_ADD app python -m app.cli add-bot --master-id 2
docker compose -f docker-compose.prod.yml exec app python -m app.cli list-bots
docker compose -f docker-compose.prod.yml exec app python -m app.cli refresh-webhook --master-id 2 [--rotate-secret]
docker compose -f docker-compose.prod.yml exec app python -m app.cli remove-bot --master-id 2
```

`add-bot` проверяет токен через `getMe`, сохраняет его зашифрованным, генерирует секреты и вызывает `setWebhook`. Токены нигде не печатаются. Один бот принадлежит одному мастеру, у одного мастера один бот. Работающий сервис подхватывает добавленных и удалённых ботов без перезапуска.

## Тесты

Тесты идут на настоящих PostgreSQL и Redis, а мокается только Telegram.

```bash
docker compose -f docker-compose.test.yml up -d --wait   # PostgreSQL :5434, Redis :6380
pip install -r requirements-dev.txt
pytest tests/ -v                                          # миграции применяются автоматически
docker compose -f docker-compose.test.yml down
```

Чтобы направить тесты на другую базу, задайте `TEST_DATABASE_URL` (имя базы должно оканчиваться на `_test`, таблицы в ней очищаются) и `TEST_REDIS_URL`. Тесты, которым нужен Redis, пропускаются с указанием причины, если он недоступен.

В наборе больше тысячи тестовых функций, с параметризацией около двух тысяч прогонов. Набор гоняли целиком на PostgreSQL 16 и Redis 7, на обоих хранилищах состояния диалогов. Тесты покрывают:

- расчёт доступности (часы, обеды, блокировки, длинные услуги, границы суток);
- создание, отмену и перенос записей, включая настоящую гонку параллельных запросов за один слот;
- напоминания: создание, однократную отправку, поведение после перезапуска, отмену вместе с записью;
- планировщик для многих мастеров: маршрутизацию, изоляцию сбоев, отсутствие дублей, горячее добавление и удаление ботов, ограничение скорости;
- обработку webhook, шифрование токенов, суперадмин-бота, пробный период;
- сквозные диалоги на обоих хранилищах состояния (`memory` и `redis`);
- миграции с нуля и между ревизиями.

Тесты-сторожи роняют сборку, если у админского обработчика нет проверки владельца, если код обращается к таблице мастера без фильтра по `master_id`, если модель создана без `master_id` или если появилось изменяемое состояние на уровне модуля. Статическую часть можно запустить отдельно и без базы: `python -m tests.static_guards`.

Стенд нагрузочного тестирования с поддельным Telegram и 100 сгенерированными мастерами лежит в `tools/loadtest` (см. его README).

## Структура репозитория

```
app/
  bot/            обработчики (клиент, админ), клавиатуры, middleware, состояния FSM
  database/       модели SQLAlchemy и репозитории
  services/       бизнес-логика: доступность, записи, напоминания, статистика, отчёты
  scheduler/      единый планировщик для всех мастеров (APScheduler)
  multibot/       webhook-сервер, реестр ботов, шифрование токенов, управление
  superadmin/     бот владельца: мастера, пробные периоды, оповещения, сводка
  tenancy/        определение мастера по апдейту
  reference/      снимок эталонного мастера и сброс к нему
```

## Безопасность

- Не коммитьте `.env`. Он есть в `.gitignore` и `.dockerignore`, в git должен лежать только `.env.example`.
- Токены ботов хранятся зашифрованными и исключены из логов, журнала действий и любого вывода. Суперадмин-бот удаляет сообщение с токеном.
- Лог Caddy настроен так, чтобы прятать секреты webhook в путях запросов. По той же причине не включайте журнал доступа.
- Админ-панель мастера открывается только его владельцу. Суперадмин-бот игнорирует всех, кого нет в белом списке.

## Ограничения

- Один экземпляр приложения на базу. Планировщик и несколько структур в памяти (допуск webhook, троттлинг отправки по ботам, кэш реестра, дедупликация оповещений) живут внутри процесса.
- Если процесс упадёт ровно в момент отправки напоминания, оно может прийти дважды.
- Часы напоминаний (24 и 2) фиксированы. Мастер может включать и выключать каждое напоминание, но не менять часы.
- Статус записи `no_show` автоматически не выставляется.
- Интерфейс бота только на русском. Приём платежей не реализован.
