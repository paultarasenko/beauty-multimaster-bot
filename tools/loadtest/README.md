# Нагрузочный стенд (этап 12B)

Стенд поднимает приложение в режиме webhook с отдельной базой `loadtest`, своим Redis и **поддельным Telegram**, создаёт 100 тестовых
мастеров и даёт цифры: время ответа webhook, ошибки, пропускную способность, скорость работы планировщика, дубли отправки,
соединения PostgreSQL, память Redis. Ничего не уходит в настоящий Telegram, настоящих токенов нет.

Он **не затрагивает рабочие контейнеры и тома**: свой проект `bbot-loadtest`, свои тома `bbot-loadtest_*`, порты только на `127.0.0.1`
(55432 — база, 18080 — приложение, 18081 — поддельный Telegram). Файл `.env` проекта стенд не читает. В рабочий образ `tools/` не попадает
(`.dockerignore`). Все команды — **из корня проекта в Git Bash**.

## 1. Поднять стенд

```bash
docker compose -f docker-compose.loadtest.yml up -d --build --wait
```

Ожидаемо: собирается образ (первый раз несколько минут), затем `postgres-loadtest`, `redis-loadtest`, `fake-telegram`, `app` — `Healthy`.
Проверка:

```bash
curl -s http://127.0.0.1:18080/ready
```

Ожидаемо: `{"status":"ready","db":"ok","redis":"ok"}`.

## 2. Заполнить тестовыми данными

```bash
docker compose -f docker-compose.loadtest.yml run --rm -T runner python -m tools.loadtest.seed --masters 100
```

Ожидаемо одна строка: `Создано: мастеров — 100, клиентов — 20000, броней — 6000, напоминаний в очереди — …` (число напоминаний около 18 000
и зависит от времени суток). Перезапуск приложения не нужен. Данные: 100 мастеров с активными ботами (фиктивные зашифрованные токены), по 5 услуг,
график пн–сб 9:00–18:00 с обедом, по 200 клиентов, по 60 броней на ближайшие 3 недели без пересечений.

Защита: стенд читает **только** `LOADTEST_DATABASE_URL` (не `DATABASE_URL`) и отказывается работать, если имя базы не начинается с `loadtest`.
Тестовые данные помечены числами ≥ 900000000000 (владелец мастера, `telegram_id` клиентов); `--cleanup` удаляет только их.

## 3. Прогоны

Каждый прогон печатает отчёт и сохраняет файлы в `tools/loadtest/results/<дата>/`. Код завершения 0 — все критерии пройдены, 1 — есть непройденные.

```bash
bash tools/loadtest/run.sh --profile normal --duration 60      # 20 апдейтов/с, ~1,5 мин
bash tools/loadtest/run.sh --profile peak --duration 60        # 100 апдейтов/с, ~1,5 мин
bash tools/loadtest/run.sh --profile storm --duration 60       # один мастер — половина трафика; сначала 20 с базовой фазы, ~2 мин
bash tools/loadtest/run.sh --profile bad_bot --duration 60     # у одного мастера «медленный» бот (ответ Telegram 8 с), ~2 мин
bash tools/loadtest/run.sh --profile bad_bot --bad-mode invalid --duration 60   # у одного мастера недействительный токен (401)
bash tools/loadtest/run.sh --profile scheduler                 # ~3000 «созревших» уведомлений; ждёт опустошения очереди (до 5 мин)
```

Полезные параметры: `--rate N` (апдейтов/с), `--warmup N` (прогон до замера, 5 с), `--fake-delay-ms N` (задержка ответа Telegram, 30 мс),
`--fake-429-share 0.05` и `--fake-403-share 0.02` (доли ответов 429 / «bot was blocked by the user»; особенно для `scheduler`),
`--notifications N`, `--hot-share`, `--bad-share`, `--bad-delay-ms`. Полный список параметров:
`docker compose -f docker-compose.loadtest.yml run --rm -T runner python -m tools.loadtest.run --help`.

Прогоны можно повторять. Каждый `scheduler` расходует ~3000 ожидающих уведомлений (их хватает примерно на 5 прогонов; потом заново `--cleanup` и `seed`).
Если бот тестового мастера был отключён планировщиком (ответ 401), следующий прогон включает его обратно и ждёт 35 секунд (кэш реестра).

Запуск без обёртки `run.sh` тоже работает (`docker compose -f docker-compose.loadtest.yml run --rm -T runner python -m tools.loadtest.run --profile normal --duration 60`),
но тогда в отчёте не будет CPU/памяти контейнеров и выписки ошибок из лога приложения.

## 4. Критерии «прошёл / не прошёл»

| Критерий | Порог | Почему так |
|---|---|---|
| Ошибок 0 (все профили) | любой ответ не 200, обрыв или таймаут (30 с) — провал | Telegram повторяет доставку при не-200; потерянный апдейт — потерянное действие клиента |
| p95 ответа webhook на `normal` | < 500 мс | при обычной нагрузке клиент не должен замечать задержку; около полусекунды чат начинает «подвисать» |
| p95 на `peak` | без порога (информативно) | цифры сравнивают с `normal` и используют на этапе 12C |
| Дублей отправки 0 (`scheduler`) | 0 повторных доставок одного текста в один чат одним ботом (считает поддельный Telegram); число доставок равно числу отметок `sent` в БД | напоминание не должно приходить дважды |
| Очередь 3000 уведомлений опустошается | ≤ 2 × интервал планировщика + 60 с (при интервале 60 с — 180 с) | планировщик тикает раз в минуту; запас на отправку при лимите 25 сообщений/с на бота; позднее напоминание теряет смысл |
| `storm`, `bad_bot`: p95 остальных мастеров | ≤ 2 × p95 базовой фазы (или разница меньше 25 мс — шум измерения) | один мастер не должен замедлять остальных |
| `bad_bot`: ошибок 0 у остальных мастеров | 0 | чужой плохой бот не ломает остальных |
| `/ready` после прогона | 200 | процесс жив, база и Redis отвечают |

Время ответа считается от **запланированного** момента отправки, а не от фактического (иначе медлительность самого генератора скрыла бы задержки
приложения); отставание генератора указано в предупреждениях отчёта.

## 5. Что прислать разработчику

Папку `tools/loadtest/results/` целиком (лучше архивом): в ней для каждого прогона

- `<время>_<профиль>_report.md` — короткий отчёт с критериями;
- `…_summary.csv` — сводные числа; `…_requests.csv` — каждый апдейт (время ответа, статус, шаг сценария);
- `…_infra.csv` — соединения PostgreSQL (`pg_stat_activity`) и память Redis по секундам; `…_queue.csv` — как опустошалась очередь (`scheduler`);
- `…_docker_stats.csv` — CPU/память контейнеров; `…_app_errors.txt` — строки ERROR/WARNING из лога приложения за прогон.

И укажите: сколько ядер и памяти у машины, на которой запускали (генератор и весь стенд работают на ней же).

## 6. Остановить и очистить

```bash
docker compose -f docker-compose.loadtest.yml run --rm -T runner python -m tools.loadtest.seed --cleanup   # удалить только тестовые данные
docker compose -f docker-compose.loadtest.yml down -v                                                       # снести стенд и ТОЛЬКО его тома
```

Ожидаемо после `--cleanup`: `Удалено: тестовых мастеров — 100, тестовых пользователей — 20000 …`. Рабочие контейнеры и тома командой `down -v` не затрагиваются (другой проект).

## Как читать цифры

- Поддельный Telegram отвечает за 30 ± 20 мс и не имитирует сеть до настоящего Telegram: реальные ответы будут чуть медленнее. Но это одинаково для всех прогонов, поэтому сравнивать профили между собой можно.
- «idle in transaction» в отчёте — соединения, которые приложение держит открытыми, пока ждёт ответа Telegram. Много таких соединений при `bad_bot` — главный признак, что плохой бот одного мастера занимает общий пул соединений.
- CPU контейнера: 100 % = одно ядро.
- Цифры зависят от машины. Если отчёт предупреждает, что «генератор отставал», перезапустите прогон на менее загруженной машине.

## Состав

`seed.py` — данные и `--cleanup`; `fake_telegram.py` — поддельный Bot API (`/__stats`, `/__reset`, `/__config`); `load.py` — генератор и сценарии;
`updates.py` — сборка апдейтов настоящими классами `CallbackData`; `run.py` + `report.py` + `collectors.py` — прогон и отчёт; `run.sh` — обёртка с замером docker stats;
`common.py` — защита базы и перцентили. Тесты: `python -m pytest tests/test_loadtest_tools.py`.
